## Legend and rule

Two dimensions are scored **separately** for every one of the 76 jobs, per the owner's requirement: an implementation gap is never reported as the only problem when the Job Book itself is incomplete.

| Design status     | Meaning                                                                                                                                |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `DESIGN_COMPLETE` | all 18 job-specific attributes present and sufficient (Y)                                                                              |
| `DESIGN_PARTIAL`  | real job-specific content, but one or more attributes generic or thin                                                                  |
| `DESIGN_STUB`     | placeholder commands (`*_typed_command`), or no upstream/downstream edges at all, or no internal DAG — a template, not a specification |

| Implementation status    | Meaning                                                                                               |
| ------------------------ | ----------------------------------------------------------------------------------------------------- |
| `IMPLEMENTED`            | job logic exists in code with tests                                                                   |
| `IMPLEMENTATION_PARTIAL` | a real supporting primitive exists and is cited, and it is named as platform substrate, not job logic |
| `IMPLEMENTATION_ABSENT`  | no code, table, tool, prompt, workflow or evaluation for the job                                      |

**Result:** 0 `DESIGN_COMPLETE` · 35 `DESIGN_PARTIAL` · 41 `DESIGN_STUB` · **0 `IMPLEMENTED`** · 0 `IMPLEMENTATION_PARTIAL` (no job has job-level code; the platform primitives are inventoried separately and are substrate, so no job is scored PARTIAL on their account) · **76 `IMPLEMENTATION_ABSENT`**.

**Scoring method for the 18 attributes (reproducible).** Each Job Book's `.json` and `.md` were parsed; a line is treated as **template boilerplate** when it recurs verbatim in ≥20 of the 76 books or in ≥90 % of its own department's books (this is what makes the department-templated facility/shipper/service-provider books score honestly — e.g. `FOT retrieval`, `normal visit`, `facility_typed_command`). Y = job-specific and sufficient; P = present but generic or thin; N = absent or placeholder. Rules per attribute are stated in §Part B. The extraction was executed by an audit-local script over the installed package (read-only) and spot-checked by hand against `carrier/dispatch` and `facility/gate`.
