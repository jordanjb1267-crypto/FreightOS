## Method and repository reality

The representative lifecycle is v1.7 `12_END_TO_END_NETWORK_WORKFLOW.md` — the 23-step brokered road shipment, its 6-hop exception propagation chain, and its evidence chain. Ownership semantics are v1.8 `03_WORK_UNIT_AND_RESPONSIBILITY_MODEL.md` (`UNASSIGNED → OWNED → HANDOFF_PENDING → OWNED_BY_NEXT → COMPLETE`; exactly one accountable job per WorkUnit; A/R/C/I per consequential transition) and `contracts/work_unit.schema.json` (`currentOwner` singular). The communication principle of v1.7 governs cross-participant steps: each participant owns its internal decision, "no central model impersonates every company", and "Agent A never directly acquires Agent B's permissions" — so the same activity legitimately has one accountable job **per participant**; a duplicate-owner risk exists only when two jobs of the **same** participant could both believe they own a step.

**Repository:** no WorkUnit, ownership record, handoff, or acceptance state exists in code, schema or migration (W0 §2: `WorkUnit|work_unit|handoff` → 0 hits; no table). At runtime **every step below is orphan** — there is nothing to own. The map therefore scores the **design**: which v1.8 job the Job Books make accountable, whether the design leaves a step without a named owner, and where two same-participant jobs overlap.

Legend — Accountable job: from the Job Books' `owns`/mission and interaction edges; **(stub)** = the book is a design stub (see [`JOB_BOOK_IMPLEMENTATION_MATRIX.md`](JOB_BOOK_IMPLEMENTATION_MATRIX.md)); Code owner today: none for all 23 steps; Module: `config/scope/module_states.yaml`.

## Part D — findings for the instruction's §7 cross-workforce proof

Finding IDs `W01-F-OWN-nn`; each is a **design** finding unless marked runtime.

1. **No accountable owner** — W01-F-OWN-01 (runtime): every step is orphan at runtime because no WorkUnit/ownership construct exists. W01-F-OWN-02 (design): steps 1, 8, 9, 10, 11, 13, 14, 15, 16, 23 have accountable jobs whose books declare no edges (facility 18, shipper 12, service provider 10, brokerage relationship_support) — 41 orphan jobs in the design graph. W01-F-OWN-03: quote-acceptance capture (step 3) and ETA revision at destination (step 13) have no named owner in any book.
2. **Multiple jobs could both believe they own it** — W01-F-OWN-04 brokerage facility_coordination vs shipment_execution (steps 8, 16) → W1 MERGE; W01-F-OWN-05 brokerage documentation vs shipment_execution (step 16); W01-F-OWN-06 facility receiving_office vs discrepancy (step 15); W01-F-OWN-07 shipper shipment_intake vs requirements (step 1); W01-F-OWN-08 shipper provider_selection vs routing_guide vs quote_analysis → W1 merges all three into one deterministic selection service; W01-F-OWN-09 brokerage shipment_execution vs tracking_communication vs relationship_support (exception hop 5) → W1 MERGE of both into shipment_execution; W01-F-OWN-10 registry facility-capacity-agent vs labor-resource-planning-agent → one v1.8 job; W01-F-OWN-11 registry autonomous-maintenance-coordinator vs carrier/maintenance_readiness → W1 MERGE. Cross-participant twins (carrier/broker/shipper tracking; carrier/facility/broker documentation; carrier/facility/shipper exception) are legitimate per v1.7 and are **not** duplicates.
3. **Free-form rather than typed handoff** — W01-F-EDGE-01: all 89 edges untyped (see [`HANDOFF_EDGE_INVENTORY.md`](HANDOFF_EDGE_INVENTORY.md)); `job_handoff.schema.json` leaves `acceptanceState` optional.
4. **Side effect without idempotency/reconciliation proof** — W01-F-OWN-12: every Job Book command (91 distinct) is a design string; the repository's idempotency primitives (N3 fingerprint, N4 intent, admin ledger, outbox `event_id`) have no job caller and there is **no reconciliation process at all** (W0 §15); the 12 settlement/pay/billing/audit jobs would need one.
5. **Deterministic job delegated to model judgment** — W01-F-OWN-13: v1.8 classes 32 roles as `agent`/`hybrid` that W1 finds deterministic or workflow (see the role matrix's "Roles that should NOT remain agents"): capacity, feasibility, tracking, settlement, risk signals, dispatch, orchestrators, appointment, gate, dock, yard, cargo readiness, custody recording, load/unload verification, invoice audit/reconciliation, pricing, billing, allocation, qualification, tender/booking, work status, capacity, eligibility, estimate, evidence.
6. **Agent without real owned outcome** — W01-F-OWN-14: brokerage relationship_support (0 edges, "handle routine communications"), shipper service_analytics (reporting), facility/service customer_communication (communication only) — outcomes are activities, not bounded business outcomes; W1 downgrades them.
7. **Architecture names a job that has no implementation** — W01-F-OWN-15: all 76 (0 implemented); additionally the 32 registry manifests name 32 agents with no runtime; the 7 AV manifests name a department v1.8 does not contain (OD-2).
8. **Implementation has a job not represented in v1.8** — W01-F-PLAT-01: N5/N6/N7 disclosure-and-transport chain, control-plane operator functions, migration authority, kill-switch operator, verified-actor binding — real responsibilities in code with no Job Book (correctly platform/human roles, but W2 contracts must reference them); W01-F-AV-01: the seven AV manifests.

## Part E — what a WorkUnit/ownership runtime would have to enforce (requirements only)

Exactly one `currentOwner` per active WorkUnit (WF-12); orphan detection beyond a routing SLA (WF-13); explicit accept/reject with a **required** acceptance state and sender retention until acceptance (WF-14/15); deadline/expiry per WorkUnit and per handoff (WF-16); tenant + legal-plane + subject partitioning; per-participant twins across the network boundary with independent authority (v1.7); an ownership event on the append-only journal so the final evidence chain (shipper commitment → broker tender → carrier assignment → facility custody → transit → receipt/POD → invoice/pay) is reconstructable (v1.7 evidence chain; WF-40). None of this exists; nothing here proposes building it in this phase.
