# ADR-N0004 — Canonical network identifier

- **ADR ID:** N0004
- **Title:** UUIDv4 as the canonical FreightOS network identifier
- **Status:** Proposed — N0 governance wiring, awaiting external rereview
- **Date:** 2026-08-10
- **Resolves:** v1.4.0 `25_DECISIONS_REQUIRED.md` decision 5 (canonical ID format and public exposure)
- **Gates:** N1. Nothing in N1 can be built without this.

## Context

Every canonical network artifact is keyed by an identifier: seven of the eight v1.4.0 schemas carry a
participant or object reference. `03_NETWORK_PARTICIPANT_IDENTITY_GRAPH.md` §2 requires an immutable
FreightOS identifier that encodes no mutable attribute and no customer-readable secret, with external
identifiers demoted to aliases.

The repository already has one convention: `gen_random_uuid()` appears 29 times across the 27
migrations, and every primary key is `uuid`. PostgreSQL 16 is the pinned baseline (ADR-0016);
`gen_random_uuid()` is native there and produces a **version 4** (random) UUID. UUIDv7 is not
available natively in PostgreSQL 16 — it would require an extension or application-side generation.

## Decision

**Canonical network identifiers are UUIDv4, generated by the database via `gen_random_uuid()`.**

| Property                             | Ruling                                                                                                                                                                                                  |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Format**                           | `uuid` (RFC 4122 version 4, 122 random bits)                                                                                                                                                            |
| **Generation authority**             | The database, as a column `DEFAULT`. Never the client, never a model, never derived from business data.                                                                                                 |
| **Public exposure**                  | Safe to expose to authorized counterparties. It is opaque, carries no attribute, no tenant, no type and no authority. Exposure still requires authorization — an opaque ID is not an access grant.      |
| **Immutability**                     | Immutable for the life of the record. Renames, mergers, re-onboarding and source-system migration never change it. Enforced in N1 by trigger.                                                           |
| **Collision handling**               | 122 random bits; collision probability is negligible. A `UNIQUE` constraint makes any collision a hard write failure rather than a silent overwrite — the database is the arbiter, not the application. |
| **Alias relationship**               | One canonical ID ↔ many namespaced external aliases (ADR-N0006). The alias never becomes the key.                                                                                                       |
| **Tenant/organization independence** | The identifier encodes neither. A participant may exist with no tenant (ADR-N0011).                                                                                                                     |

## Alternatives considered

**UUIDv7 (time-ordered).** Rejected for canonical network IDs on two grounds, one privacy and one
practical. It embeds a millisecond creation timestamp, so an externally exposed v7 ID discloses when
a participant was onboarded and lets a counterparty order and rate-estimate a competitor's network
growth — a real leak for a network whose neutrality is a stated principle (`00_MASTER_HANDOFF.md`
§2.11). Its advantage is index locality under high insert volume, which does not apply to
participants: organizations, facilities and agents are low-cardinality and rarely written.

**ULID or another sortable opaque identifier.** Rejected for the same timestamp-disclosure reason,
plus it is not a native PostgreSQL type, so it would be stored as text and lose `uuid` comparison and
storage efficiency for no benefit here.

**Internal surrogate + separate externally exposed opaque ID.** Rejected as premature. It solves
enumeration and correlation exposure, which UUIDv4 does not suffer from — v4 is already
unguessable and attribute-free. Two identifiers per object doubles the join surface and creates a
class of bug where the wrong one is published. Revisit only if a future requirement demands rotating
an external identifier while keeping the internal one stable.

**Deliberately left open:** the identifier strategy for high-volume **event** IDs. Write locality is
a genuine consideration at event scale, unlike participant scale, and the tradeoff is different. That
belongs to N3, decided on N3's evidence, and this ADR does not settle it.

## Identity/authority impact

None. An identifier confers nothing (ADR-N0003).

## Data ownership/privacy impact

Attribute-free and timestamp-free by construction, which is the reason v4 was chosen over v7.

## Interoperability impact

External systems continue to use their own identifiers; those enter as aliases. FreightOS never
adopts a partner identifier as its key, which is what keeps a partner's renumbering from becoming a
FreightOS migration.

## Migration and rollback

None in N0. N1 columns are `uuid ... DEFAULT gen_random_uuid()`, consistent with all 27 existing
migrations, so no new extension and no new dependency.

## Acceptance evidence

N1 must prove: ID immutability under `UPDATE`; uniqueness enforced by constraint; no ID derived from
tenant, organization, type or any business attribute.

## Open decisions

Event-ID generation strategy (N3). Whether any canonical ID is ever surfaced in a URL path, which is
an API-surface question and belongs to N13.
